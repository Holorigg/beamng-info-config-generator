# Implementation References

## BeamNG metadata

[Making configurations and info files](https://documentation.beamng.com/modding/vehicle/tutorials/configs/)
describes info files alongside the PC file. Configuration is the display name.
New files use the actual PC stem; historical alternatives remain scan
fallbacks, without renaming existing user files.

[Default paints](https://documentation.beamng.com/modding/vehicle/vehicle_paints/paint_definition/)
also lives in metadata, so an ordinary form save must merge fields instead of
replacing the entire document.

The [BeamNG team's performance statistics thread](https://beamng.com/threads/performance-statistics-feedback-thread.28306/)
describes measured statistics generated by the game, requiring existing info
files. Its launch commands were last edited in 2018 and must be checked against
the installed game before automation is added. This application creates and
edits metadata; it does not measure horsepower, acceleration, or braking.

The [configuration guide](https://www.beamng.com/threads/ultimate-step-by-step-guide-how-to-make-a-configuration-with-description-and-stats.85837/)
provides additional authoring context.

## Career compatibility

[RLS vehicle shopping source](https://github.com/RLS-Modding/rls_career_overhaul/blob/main/lua/ge/extensions/overrides/career/modules/vehicleShopping.lua)
handles seller selection, model years, population, and other game state.
Passing this tool's metadata checks does not guarantee a dealer listing:
requirements depend on the installed game/mod and dealer filters. Existing
years and custom properties are retained, not fabricated from part names.

## File handling and UI

[Python zipfile documentation](https://docs.python.org/3/library/zipfile.html)
documents streaming access, entry metadata, ZIP64, and append mode. Existing
ZipInfo objects must be copied before writing, because the writer changes their
offsets. Automatic append saves only the overwritten central-directory tail
for rollback on caught errors; it is not a guarantee against power loss.
Disk/RAM replacements commit through a temporary file next to the original.

[Qt threading documentation](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html)
guides worker lifetime and signal delivery. Progress and completion are received
by QObject slots in the GUI thread, and cancellation is cooperative.

[PyJSON5](https://pyjson5.k6i.de/en/latest/) provides a compiled JSON5 parser.
Standard JSON uses the built-in parser first; relaxed documents fall back to
PyJSON5. A small token-aware compatibility repair handles missing commas
between fields on different lines, preserving string/comment contents.

[PyInstaller usage](https://pyinstaller.org/en/stable/usage.html) informs Windows
packaging. The packaged application has a noninteractive smoke-test entry point.
The build script uses a restricted DLL search PATH so unrelated applications'
ICU or Qt libraries cannot be bundled accidentally. Smoke checks exercise JSON5
and temporary archive roundtrips as well as UI initialization.

## Preservation and write safety

Ordinary form saves start with the existing metadata object and update the
fields represented by the editor. This matters because BeamNG metadata can
contain paints, years, and mod-specific properties that are outside this tool's
form. Explicit regeneration is different: it creates a new document from
current defaults, after a confirmation prompt. Repair updates invalid required
values while retaining other keys; files that cannot be parsed are skipped
during bulk repair.

Folder metadata is written to a same-directory temporary file, flushed, and
replaced atomically where the filesystem supports replacement semantics. For
ZIPs, new files in Automatic mode use append; caught append errors restore the
old central-directory tail. This is a narrow rollback strategy, not a durable
transaction against power loss, process termination, or storage-device failure.
Replacements and explicit Disk/RAM modes build a temporary archive beside the
source and replace it after completion. Existing archive comments and copied
entry metadata are retained, and file payloads are streamed in bounded chunks.
Temporary output requires free disk space. RAM mode additionally holds the
compressed rebuilt archive in memory before writing the temporary file, which
can be costly for large archives.

Optional dated backups are copies adjacent to the original file. They are a
useful recovery point, but a ZIP backup needs free space equal to the complete
archive. Cancellation is cooperative: it prevents later work and interrupts
copy/write loops at checks, while already completed archive groups remain
committed. Operation history records completed counts, cancellation, and
errors; it is not a persistent transaction journal.

## Validation and verification limits

The validity indicator checks the application's required metadata profile:
nonempty text for Configuration, Config Type, Drivetrain, Transmission, and
Fuel Type, and a finite positive Value. It is not an in-game compatibility
test. Detection based on part names is heuristic, and performance figures are
not simulated or measured by the application.

Automated tests use temporary files and fixtures, including malformed archives,
write failures, cancellation, JSON preservation, and headless UI interactions.
The packaged smoke test exercises JSON/ZIP roundtrips against temporary data
and initializes packaged UI assets. These checks do not amount to testing with
BeamNG.drive or installed user mods.
